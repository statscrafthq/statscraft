# Contributing to Statscraft

This page is for developers. The [developer notes](docs/developers/README.md) describe the settings file, updates, sessions and output files, and [Writing a plugin](docs/developers/plugins.md) the plugin protocol.

## Build from source

You need Rust 1.95 or newer (`rustc --version` shows yours; `rustup update stable` gets a newer one).

```
git clone https://github.com/statscrafthq/statscraft
cd statscraft
cargo build --release -p statscraft -p statscraft-gui
```

The programs are then in `target/release/`: `statscraft`, the command line, and `statscraft-gui`, the window. Put `target/release` on your `PATH`, or call them by their full path. `cargo run -p statscraft-gui -- survey.sav job.sps` starts the window from the checkout with a data file and a syntax file.

A copy built from source does not update itself: pull and build again.

## Getting a build

The workflow **Release build** (started by hand: Actions, Release build, Run workflow, or `gh workflow run release.yml`) gives a per-user Windows installer and a portable Windows .zip, a .deb for Debian and Ubuntu, a .tar.gz for other Linux, and a .tar.gz for macOS (Apple silicon and Intel) with Statscraft.app and the command line, each with `statscraft` and `statscraft-gui`, an MCP bundle (.mcpb) for Claude Desktop on each of the three systems, the agent skill as a .zip, and a `SHA256SUMS` of them; ticking **draft release** also attaches them to a draft GitHub Release. [Install and update](docs/install.md) explains how users install and uninstall them. The packaging scripts are in `packaging/`, the icon in `crates/gui/icons/`.

## Changelog

Write each entry in CHANGELOG.md under "Unreleased" for a user: one line per change, saying what a user can now do. No option-by-option lists, no test or verification notes, no comparisons with other software, no internal history. The same holds for the help text and the guides: they describe only what Statscraft does.

## Releasing a version

1. Set the new version in `[workspace.package]` of the root `Cargo.toml` (for example `version = "0.2.0"`) and in `plugins/statscraft/.claude-plugin/plugin.json` (a test checks that they agree), run `cargo build` so `Cargo.lock` follows, and commit and push to `main`.
2. Run the **Release build** workflow on `main` with **draft release** ticked (`gh workflow run release.yml -f draft_release=true`). It builds the packages and creates a draft release `v0.2.0` with them, a `SHA256SUMS` file and notes generated from the commits.
3. Review the draft on the Releases page: edit the notes, and try the packages if you like.
4. Publish it. Only then do the windows and `statscraft update` see it; the workflow never publishes by itself.

The updaters compare the release tag `vX.Y.Z` with their own version, so every release needs a higher version in `Cargo.toml`.

## Development

```
cargo test
```

After cloning, run `git config core.hooksPath .githooks` once. The hooks keep vendor and product names of other companies out of the repository.

Test data lives in `tests/fixtures/`. It is synthetic and generated by the scripts in that folder. The sample file of the guides, `docs/sample/survey.sav`, is made by `docs/sample/make-survey.sps`: run `statscraft run make-survey.sps` in that folder.

The command pages in `docs/commands/` are generated from the command table in `crates/syntax/src/table.rs`. A test fails when they are out of date; regenerate them with:

```
UPDATE_DOCS=1 cargo test -p statscraft-syntax --test command_docs
```

The OpenStatSpec conformance tests (`crates/openstatspec/tests/conformance.rs` and the database runners) read the published manifests from a local checkout of the specification: the folder in `OPENSTATSPEC_DIR`, or `openStatSpec/specification` next to any parent folder of the repository. Without it the test is skipped, except in CI, where it fails. CI checks out the specification at the commit in `crates/openstatspec/spec-commit`; to move to a new spec tag, change that line to the tag's commit and `SPECIFICATION_RELEASE` in `crates/openstatspec/src/db.rs` to the tag's name, which the capability declaration (`statscraft db capabilities`) reports.
